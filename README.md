# 엣지알리미 (Edge Alimi)

**인력난 현장을 위한 저비용 엣지 AI 예지보전 모듈** — 설비 고장 전조 감지 시스템

> **라이브 데모 (장비·설치 불필요)**: https://suummu.github.io/edge_module/
> 브라우저/폰에서 바로 감시 콘솔을 열어 학습→감시→결함 주입→정지→드리프트
> 전체 흐름을 데모 시뮬레이터로 시연할 수 있다.

회전 기계(모터·팬·펌프·컨베이어)는 고장 전에 진동·전류·온도가 먼저 변한다.
엣지알리미는 3만 원 이하의 저가 센서 + ESP32로 이 변화를 현장에서 직접 판별해
고장을 사전 경보한다. 클라우드 없이 센서단에서 즉시 판정하므로,

- **망분리(air-gap) 환경**에서 클라우드형 솔루션이 아예 동작할 수 없는 현장과
- **축적 데이터·제조사 기준값이 없는 비표준/노후 설비**를

현장 자가 학습(정상 데이터만으로 개별 baseline 수립)으로 감시할 수 있다.
대상: 중소·중견 제조, 물류센터, 상하수도·전력 등 무인 공공 인프라, 군.

향후 수요처로는 데이터센터·반도체 팹 확산에 따른 냉각수 순환·방류 펌프 계통도
있다 — 두 업종 모두 냉각수 계통에 모터·펌프가 필수이고, 보안 민감도가 높아
클라우드 연결을 꺼릴 유인이 커서 망분리 포지셔닝과 맞는 방향이다. (구체 수요
규모는 아직 별도 검증 전 — 수치 근거 확보 시 갱신) *(26-08-20부로 수정됨)*

> 한 줄 포지셔닝: **"망분리 환경에서, 축적 데이터가 없는 비표준 설비를,
> 현장에서 자가 학습해 감시한다."**

## 저장소 구조

```
src/               파이썬 설계도 — 로직의 원본 (시뮬레이션 검증)
ml/                공개 실데이터 검증 (CWRU 베어링 · MaFaulDa 불평형/정렬불량)
  results/           성능 수치(JSON) + 혼동행렬·특징분포·중요도 그림
edge_module_c/     C/C++ 실장 시스템 — 파이썬 설계를 ESP32 실기기용으로 포팅
  core/              순수 C 코어 (ESP32/PC 동일 컴파일, 단일 진실)
  esp32/             ESP32 펌웨어 (NVS 영속화, 센서장애 격리, 콘솔 내장 서빙)
  pc_test/           하드웨어 없는 자동 검증 하니스 (24항목)
  pi/                라즈베리파이 서버 (수집·이력·콘솔 서빙)
  viz/               감시 콘솔 (단일 HTML, PWA — 폰 홈 화면 설치)
  tools/             대시보드 → 펌웨어 임베딩 도구
c/                 이식 정합성 레퍼런스 구현 (C99 단일 파일) + 파이썬 대조 검증
                   ml/ 이 내보낸 온디바이스 분류기 헤더(ml_model_*.h) 포함
esp32/             실센서 포트 v2 (교차검증 벡터 내장, VALIDATION_MODE)
tools/             테스트벡터 내보내기 · 오차분석 그림 생성
analysis/          포팅 오차 · 해상도 증폭 · 민감도 열화 정량화 그림
docs/              GitHub Pages 공개 데모 (viz/ 콘솔의 배포 사본)
```

파이썬(`src/`)은 로직을 설계·검증하는 원본이고, C(`edge_module_c/`)는 그것을
실기기에서 돌리는 실장본이다. 두 구현은 같은 판정 로직(ACTIVE_FEATURES, 3σ +
연속성 필터, 드리프트 감시, 회전수 기준축)을 공유하며, 로직 변경은 파이썬에서
먼저 검증한 뒤 C에 반영하는 것을 원칙으로 한다.

검증은 성격이 다른 두 축으로 나뉜다. `edge_module_c/pc_test/`는 **거동**을
검증하고(시나리오 A/B, 드리프트, 정지 오경보, 스냅샷 복원 등 24항목),
`c/validate_main.c`는 **수치**를 검증한다(파이썬 float64 정답값 대비 C float32
상대오차 2% 이내). 전자는 "옳게 동작하는가", 후자는 "이식하면서 값이
변하지 않았는가"에 답한다.

## 시스템 아키텍처 — 3계층

```
[ESP32 "계산기"]  센서 → FFT → 특징추출 → 3σ 판정 → 결과만 송출 (해석·시각화 없음)
       │ JSON (Wi-Fi HTTP / 시리얼)
[라즈베리파이 "도서관"]  판정·특징값 축적(JSONL), 이력 API, 콘솔 서빙
       │ http://<pi-ip>:8080
[브라우저/폰 "디스플레이"]  어떤 지표가·얼마나·어떤 추세로 이탈했는지 표시
```

센서: MPU-6050(진동, 메인) + ACS712(전류) + 서미스터(온도), 목표 단가 3만 원 이하.

## 감지 범위 (명시적 스코프)

| 결함 | 시그니처 | 상태 |
|---|---|---|
| 불평형 (unbalance) | 1× 방사 진동 증가 | **대상** |
| 정렬불량 (misalignment) | 2× + 축방향 | **대상** |
| 기계적 이완 (looseness) | 1× 고조파(2×/3×/4×) | **대상** |
| 베어링 정밀 진단 | 1–20kHz 충격 + 포락선 분석 | 범위 밖 (센서 대역 한계) |
| 잔여수명(RUL)·고장 유형 다중분류 | — | 범위 밖 (향후 확장) |

*(26-08-20부로 수정됨)*
베어링 대역을 커버할 센서 확장(ADXL345 등 저가 디지털 가속도계 병행, ADXL1001/1002
같은 산업용 고대역 아날로그 소자)도 검토는 해봤다. 결론은 둘 다 "3만 원 이하"
제약과 충돌: 저가 디지털 대안은 실사용 대역이 여전히 1~20kHz에 못 미치고,
목표 대역을 실제로 커버하는 아날로그 소자는 안티앨리어싱 필터·외부 고속
ADC·저노이즈 전원까지 신호처리 서브시스템 하나를 통째로 새로 설계해야 해서
예산·난이도 모두 벗어난다. 그래서 베어링 정밀 진단은 위 표대로 스코프 밖으로
확정하고, MPU-6050 단일 센서로 갈 수 있는 3개 결함 유형에 집중했다.

정상-only 학습은 "무언가 평소와 다르다"까지 말한다 — **조기경보이지 진단이
아니며**, 이것이 라벨링된 고장 데이터가 존재하지 않는 현장(중요 설비일수록
고장이 안 나서 데이터가 없다)에서 성립하는 유일한 현실적 접근이다.
콘솔이 지표별 이탈 정도(z-score)와 추세를 보여줌으로써 해석 인력 공백과
경보 피로를 완충한다.

## 판정 로직 요약 (파이썬·C 공통)

- **특징 (ACTIVE_FEATURES)**: `rms`(전체 진동 에너지, 절대량),
  `harmonic1_ratio`(1× 대역 / 전체 에너지, 불평형), `harmonic2_ratio`(2×,
  정렬불량), `harmonic3_ratio`(3×, 이완), `high_freq_ratio`(보조 지표 —
  베어링 정밀 진단 아님, 상한은 센서 유효대역 이내로 제한).
  `kurtosis`(베어링류 지표, 범위 밖)·`peak_freq`(변별력 부족)는 판별용 제외.
  **(v2)** 대역 에너지를 전체 에너지 대비 **비율**로 정규화 — 아래
  [현재 상태](#현재-상태-정직하게)의 공개 실데이터 검증에서 쓴 특징
  정의와 실장을 일치시켰고, 부가로 회전수 변화에 따른 전체 진폭 변동이
  분자·분모에서 상쇄돼 가변속 설비에서도 단일 baseline이 가능해졌다.
- **기준축**: 고조파 대역은 고정 Hz가 아니라 매 윈도 추정하는
  `rotation_hz_estimate`(정격 RPM 파생 탐색범위 내 최대 피크 + 점프 거부)
  기준으로 상대 배치 — 부하로 RPM이 흔들려도 대역이 고조파를 놓치지 않는다.
  **(v2)** 대역 반폭(`harmonic_bw_hz`)을 물리 허용오차(±5Hz) + Hann 창
  주엽 2bin 폭으로 재계산해, 회전수 추정이 bin 경계에 걸려도 에너지
  포획률이 유지되도록 했다.
- **판정**: 각 설비에서 자가 학습한 정상 baseline(평균+3σ) 이탈 → 1차 의심,
  연속 윈도 확인(confirm_window)을 거쳐야 확정 이상. 오탐 억제의 대가로
  확정까지 최소 수 윈도의 지연이 생기는 **설계된 트레이드오프**이며,
  두 지표(Scenario A 오탐율 / Scenario B 감지 지연)를 항상 함께 보고한다.
  **(v2)** 판정 공간을 `log(x + eps)`로 변환한 뒤 3σ를 적용한다 — 대역
  에너지/비율은 오른쪽 꼬리가 긴 분포라 선형 3σ 상단이 정상 상태에서도
  자주 뚫렸다(시뮬레이션 실측 오탐 1.41% → log 변환 후 0.31%). baseline
  통계·판정·드리프트가 전부 같은 log 공간을 쓰며, 스냅샷도 그 공간의
  값으로 저장된다.
- **위험 정상화 방지**: 최초 baseline(`original_means`)을 별도 보존해,
  서서히 나빠지는 것을 "새로운 정상"으로 착각하지 않도록 드리프트 경고를 낸다.
- **실무 안전장치 (C 실장)**: 설비 정지 자동 판별(정지≠이상), 센서 장애
  격리(센서 고장≠설비 이상), baseline 정전 영속화, 기동 과도 구간 학습 배제.

각 구현의 상세는 [`src/` 모듈별 설명(이전 README)](https://github.com/suummu/edge_module/blob/1ad5427/README.md)과
[`edge_module_c/README.md`](edge_module_c/README.md)를 참조.

### v2 — 검증 특징과 실장 특징 일치, log-space 3σ, 센서 대역 상한

기존 실장은 절대 대역 에너지에 대칭 3σ를 썼는데, 공개 실데이터 검증
([현재 상태](#현재-상태-정직하게)의 90.2%/82.5%)은 비율 정규화 특징으로
얻은 수치였다 — 검증한 알고리즘과 실장이 서로 달랐던 불일치다. v2는
이 세 가지를 고쳤다.

1. **비율 정규화**: 대역 에너지를 전체 에너지 대비 비율로 바꿔 검증
   수치와 실장을 일치시켰다.
2. **log-space 3σ**: 에너지/비율의 비대칭 분포에 선형 3σ를 적용하던
   것을 `log(x+eps)` 공간에서의 3σ로 바꿔 오탐을 줄였다.
3. **센서 유효대역 상한**: 고주파 특징의 상한을 Nyquist(500Hz)에서
   MPU-6050 DLPF=0 유효대역(260Hz) 이내로 제한 — 기존 상한은 필터
   감쇠 구간의 센서 노이즈를 특징으로 재고 있었다.

검증: 새 이식 대조 하니스(`edge_module_c/pc_test/validate_v2.c`)가
파이썬 float64 정답 대비 최대 상대오차 2.8e-06로 PASS, 기존 거동 검증
28항목도 v2 코어로 재실행해 전체 PASS. 해석적 파이썬 구현은
`src/feature_extraction_v2.py` · `tests/validate_v2.py`.

## 로컬 이벤트 로그 저장 전략 (제안, 미구현) *(26-08-20부로 수정됨)*

Pi 없이 ESP32 단독으로도 확정 이상 이력을 남길 수 있는지 검토했다. 지금 NVS(`Preferences`)는
baseline 값 저장에만 쓰이고 있고, 이벤트 로그 기능 자체는 아직 없다 — 아래는 구현 방향 제안이다.

- **저장 대상을 좁힌다**: 매 윈도우의 1차 의심(`is_suspect`)이 아니라, 연속성 필터를 통과한
  확정 이상(`is_anomaly`)과 드리프트 경고만 남긴다. 이 필터링 하나가 저장 기간을
  하루 단위에서 연 단위로 바꾼다.
- **레코드는 26바이트 바이너리**로 저장한다(uptime 4B + event_type 1B + trigger_mask 1B +
  특징값 5개 20B). JSON/CSV 텍스트보다 3~5배 작다.
- **저장 계층은 LittleFS**(SPIFFS보다 정전에 강함), 기존 4MB 모듈·기본 파티션 그대로 사용 —
  추가 부품·설정 변경 불필요.
- **조회는 기존 API 패턴을 확장**: `GET /data`, `/health` 옆에 `GET /log?n=50`을 추가해
  브라우저가 직접 읽도록 한다. 나중에 Pi를 얹어도 이 엔드포인트를 그대로 프록시하면 되므로
  구조가 깨지지 않는다.

### 실제 저장 가능 용량 (계산 근거: 26B/레코드, LittleFS 오버헤드 10% 반영)

| 구성 | 실사용 용량 | 하루 1건 | 하루 20건 (설비가 계속 이상 상태) | 하루 120건 (시간당 5건, 사실상 baseline 오류) |
|---|---|---|---|---|
| 4MB 모듈, 기본 파티션(그대로) | 약 1.35 MB | ~149년 | ~7.5년 | ~1.24년 |
| 4MB 모듈, 파티션 커스텀(fs 2.5MiB) | 약 2.25 MB | ~249년 | ~12.4년 | ~2.07년 |
| 8MB(WROVER) 모듈 | 약 2.7 MB | ~298년 | ~14.9년 | ~2.49년 |

하루 120건(시간당 5건꼴 지속 경보)은 연속성 필터를 계속 통과하고 있다는 뜻이라, 정상 운영이
아니라 설비 정지 또는 baseline 재학습이 필요한 상태로 봐야 한다. 그런 극단적 경우조차 기본
구성으로 1년 이상 버티므로, 이 프로젝트의 실사용 기간 대비 SD카드·Pi 없이 ESP32 단독 저장으로
충분하다.

## 현재 상태 (정직하게)

**된 것**
- 파이프라인 로직 설계·시뮬레이션 검증 (파이썬)
- C 전체 시스템 실장: 코어 + ESP32 펌웨어 + Pi 서버 + 콘솔(PWA), 24항목 자동 검증
- 실무 감사 반영: 정지 오경보 차단, 센서 장애 격리, baseline 영속화 등
- **공개 실데이터 검증** — 합성 신호로 설계한 판정 로직을 실제 회전기계 데이터에
  그대로 적용 (`ml/results/`):

  | | CWRU (베어링) | MaFaulDa (불평형/정렬불량) |
  |---|---|---|
  | 3σ 탐지율 | 3개 결함 전부 100% | 불평형 74.4% / 정렬불량 56.9% |
  | 회전수 구간별 baseline 적용 | — | **불평형 90.2% / 정렬불량 82.5%** |
  | 3σ 오탐율 (정상) | 4.83% → **확정 기준 1.81%** | **0%** |
  | Isolation Forest 대조 | 탐지 동일, 오탐 2.42% | 탐지 62.9/39.1%로 **열세** |

  회전수를 기준축으로 잡으면 탐지율이 74/57 → 90/82로 뛴다 — "회전수를 모르면
  진동 분석이 무의미하다"는 자문이 실데이터로 재현된 결과다. sklearn 없이 돌아가는
  3σ가 Isolation Forest 대비 열세가 아니라는 것도 확인됐다(MaFaulDa에서는 우위).
- **파이썬 ↔ C 수치 대조 검증** — 동일 입력에 대해 특징값·baseline·3σ 판별 불리언이
  상대오차 2% 이내로 일치 (`c/validate_main.c`, 벡터는 `tools/export_test_vectors.py` 생성)

**안 된 것**
- **자체 실측 데이터: 여전히 없음.** 위 수치는 실험실 장비로 측정된 공개
  데이터이며, 저가 MEMS 센서(MPU-6050) 환경의 성능을 보장하지 않는다.
  시뮬레이션 기준 Scenario A/B 수치도 실기기 데이터로 재측정해야 한다.
- **경미한 결함은 놓친다.** MaFaulDa 심각도별로 보면 불평형 35g은 98.9%지만 6g은
  50%, 정렬불량 2.0mm는 75.9%지만 1.0mm는 37.9%다. 확정 판정 기준으로는 고장
  파일 24개 중 16개만 경보가 울렸다. 조기 경보의 실제 민감도 하한이다.
- ESP32 실기기 실측 미완: 실효 샘플링, FFT 처리 시간, NVS 동작, gzip 서빙.
- 실데이터 대기 중인 파라미터: 절대 RMS 임계값(데이터시트 필요), 드리프트
  윈도/시그마, 가동판별 SNR 임계값(배경 진동 심한 현장).
