# 엣지알리미 (Edge Alimi)

**인력난 현장을 위한 저비용 엣지 AI 예지보전 모듈** — 설비 고장 전조 감지 시스템

회전 기계(모터·팬·펌프·컨베이어)는 고장 전에 진동·전류·온도가 먼저 변한다.
엣지알리미는 3만 원 이하의 저가 센서 + ESP32로 이 변화를 현장에서 직접 판별해
고장을 사전 경보한다. 클라우드 없이 센서단에서 즉시 판정하므로,

- **망분리(air-gap) 환경**에서 클라우드형 솔루션이 아예 동작할 수 없는 현장과
- **축적 데이터·제조사 기준값이 없는 비표준/노후 설비**를

현장 자가 학습(정상 데이터만으로 개별 baseline 수립)으로 감시할 수 있다.
대상: 중소·중견 제조, 물류센터, 상하수도·전력 등 무인 공공 인프라, 군.

> 한 줄 포지셔닝: **"망분리 환경에서, 축적 데이터가 없는 비표준 설비를,
> 현장에서 자가 학습해 감시한다."**

## 저장소 구조

```
src/               파이썬 설계도 — 로직의 원본 (시뮬레이션 검증)
edge_module_c/     C/C++ 실장 시스템 — 파이썬 설계를 ESP32 실기기용으로 포팅
  core/              순수 C 코어 (ESP32/PC 동일 컴파일, 단일 진실)
  esp32/             ESP32 펌웨어 (NVS 영속화, 센서장애 격리, 콘솔 내장 서빙)
  pc_test/           하드웨어 없는 자동 검증 하니스 (24항목)
  pi/                라즈베리파이 서버 (수집·이력·콘솔 서빙)
  viz/               감시 콘솔 (단일 HTML, PWA — 폰 홈 화면 설치)
  tools/             대시보드 → 펌웨어 임베딩 도구
```

파이썬(`src/`)은 로직을 설계·검증하는 원본이고, C(`edge_module_c/`)는 그것을
실기기에서 돌리는 실장본이다. 두 구현은 같은 판정 로직(ACTIVE_FEATURES, 3σ +
연속성 필터, 드리프트 감시, 회전수 기준축)을 공유하며, 로직 변경은 파이썬에서
먼저 검증한 뒤 C에 반영하는 것을 원칙으로 한다.

## 시스템 아키텍처 — 3계층

```
[ESP32 "계산기"]  센서 → FFT → 특징추출 → 3σ 판정 → 결과만 송출 (해석·시각화 없음)
       │ JSON (Wi-Fi HTTP / 시리얼)
[라즈베리파이 "도서관"]  판정·특징값 축적(JSONL), 이력 API, 콘솔 서빙
       │ http://<pi-ip>:8080
[브라우저/폰 "디스플레이"]  어떤 지표가·얼마나·어떤 추세로 이탈했는지 표시
```

센서: MPU-6050(진동, 메인) + ACS712(전류) + 서미스터(온도), 목표 단가 3만 원 이하.

## 감지 범위 (명시적 스코프)

| 결함 | 시그니처 | 상태 |
|---|---|---|
| 불평형 (unbalance) | 1× 방사 진동 증가 | **대상** |
| 정렬불량 (misalignment) | 2× + 축방향 | **대상** |
| 기계적 이완 (looseness) | 1× 고조파(2×/3×/4×) | **대상** |
| 베어링 정밀 진단 | 1–20kHz 충격 + 포락선 분석 | 범위 밖 (센서 대역 한계) |
| 잔여수명(RUL)·고장 유형 다중분류 | — | 범위 밖 (향후 확장) |

정상-only 학습은 "무언가 평소와 다르다"까지 말한다 — **조기경보이지 진단이
아니며**, 이것이 라벨링된 고장 데이터가 존재하지 않는 현장(중요 설비일수록
고장이 안 나서 데이터가 없다)에서 성립하는 유일한 현실적 접근이다.
콘솔이 지표별 이탈 정도(z-score)와 추세를 보여줌으로써 해석 인력 공백과
경보 피로를 완충한다.

## 빠른 시작

### A. 파이썬 설계도 검증 (시뮬레이션)

```bash
pip install -r requirements.txt
python -m src.signal_generator      # 가짜 진동 신호 확인
python -m src.baseline_detector     # 3σ + 연속성 필터 판정 (핵심)
python -m src.visualize             # 그래프 4장 → outputs/
```

### B. C 코어 검증 (하드웨어 불필요)

```bash
cd edge_module_c/pc_test
gcc -O2 -Wall -Wextra -o em_test main.c ../core/em_*.c -lm && ./em_test
```

24항목 자동 검증: 확정 오탐 0/500윈도, 4개 결함 유형 감지 지연(정직 기록),
드리프트 발화, 재-fit 후 원본 baseline 보존, 타 RPM + 회전수 ±8% 드리프트
강건성, **설비 정지/재가동 오경보 차단**, baseline 스냅샷 저장/복원/손상 거부.

### C. 실기기 배포

```bash
# 1) ESP32: Arduino IDE 로 edge_module_c/esp32/edge_alimi/ 업로드
#    (WIFI_SSID / RATED_RPM_DEFAULT 수정 — 정격 RPM 이 유일한 필수 설정)
# 2) 브라우저에서 http://<esp32-ip>/ 접속 → 콘솔이 뜸 (펌웨어 내장 서빙)
# 3) [정상 기준선 학습] → 약 2분 → 감시 시작 (완료 시 NVS 자동 저장)

# 선택: Pi 도서관 계층 (이력 축적 + 콘솔 서빙)
python3 edge_module_c/pi/pi_server.py http://<esp32-ip> --port 8080
```

### D. 모바일 앱 (PWA)

콘솔 접속 → Android Chrome "홈 화면에 추가" / iOS Safari 공유 → "홈 화면에
추가". 전용 아이콘 + 전체화면 앱으로 실행된다 (스토어·APK 불필요).
장비가 없어도 콘솔의 **데모 시뮬레이터 모드**로 학습→감시→결함 주입→정지→
드리프트 전체 흐름을 시연할 수 있다.

## 판정 로직 요약 (파이썬·C 공통)

- **특징 (ACTIVE_FEATURES)**: `rms`, `harmonic1_energy`(1×, 불평형),
  `harmonic2_energy`(2×, 정렬불량), `harmonic3_energy`(3×, 이완),
  `high_freq_energy`(보조 지표 — 베어링 정밀 진단 아님).
  `kurtosis`(베어링류 지표, 범위 밖)·`peak_freq`(변별력 부족)는 판별용 제외.
- **기준축**: 고조파 대역은 고정 Hz가 아니라 매 윈도 추정하는
  `rotation_hz_estimate`(정격 RPM 파생 탐색범위 내 최대 피크 + 점프 거부)
  기준으로 상대 배치 — 부하로 RPM이 흔들려도 대역이 고조파를 놓치지 않는다.
- **판정**: 각 설비에서 자가 학습한 정상 baseline(평균+3σ) 이탈 → 1차 의심,
  연속 윈도 확인(confirm_window)을 거쳐야 확정 이상. 오탐 억제의 대가로
  확정까지 최소 수 윈도의 지연이 생기는 **설계된 트레이드오프**이며,
  두 지표(Scenario A 오탐율 / Scenario B 감지 지연)를 항상 함께 보고한다.
- **위험 정상화 방지**: 최초 baseline(`original_means`)을 별도 보존해,
  서서히 나빠지는 것을 "새로운 정상"으로 착각하지 않도록 드리프트 경고를 낸다.
- **실무 안전장치 (C 실장)**: 설비 정지 자동 판별(정지≠이상), 센서 장애
  격리(센서 고장≠설비 이상), baseline 정전 영속화, 기동 과도 구간 학습 배제.

각 구현의 상세는 [`src/` 모듈별 설명(이전 README)](https://github.com/suummu/edge_module/blob/1ad5427/README.md)과
[`edge_module_c/README.md`](edge_module_c/README.md)를 참조.

## 현재 상태 (정직하게)

**된 것**
- 파이프라인 로직 설계·시뮬레이션 검증 (파이썬)
- C 전체 시스템 실장: 코어 + ESP32 펌웨어 + Pi 서버 + 콘솔(PWA), 24항목 자동 검증
- 실무 감사 반영: 정지 오경보 차단, 센서 장애 격리, baseline 영속화 등

**안 된 것**
- **실제 정상/고장 진동 데이터: 여전히 없음.** 모든 성능 수치는 합성 신호 기준이며
  실기기 데이터 확보 후 재측정해야 한다.
- ESP32 실기기 실측 미완: 실효 샘플링, FFT 처리 시간, NVS 동작, gzip 서빙.
- 실데이터 대기 중인 파라미터: 절대 RMS 임계값(데이터시트 필요), 드리프트
  윈도/시그마, 가동판별 SNR 임계값(배경 진동 심한 현장).
